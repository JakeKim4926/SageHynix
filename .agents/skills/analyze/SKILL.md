# Analyze

목표: 데이터 주제를 몰라도 틀린 숫자가 나오는 경로를 막는다. 기법은 여기서 고르지 않는다 — 고른 기법과 이유는 ledger decision(D-n)으로 남긴다.

## ① 데이터를 처음 열 때 (과제당 1회, 데이터가 추가되면 그 파일만)
1. 원본 데이터는 읽기만 한다. 가공본은 별도 경로에 쓰고 원본을 덮어쓰지 않는다.
2. 프로파일을 `docs/research/data-profile.md`의 `## 근거`에 남긴다.
   - 표 데이터(CSV·TSV·JSONL): `python3 .agents/skills/analyze/scripts/profile_data.py <파일>...` 출력을 그대로 붙인다. 출력은 사실만이다.
   - Excel·Parquet 등 스크립트가 읽지 않는 표: pandas로 열어 같은 항목(행·열·중복·열별 타입·결측률·고유값·범위)을 직접 적는다. pandas만으로는 못 읽는다 — xlsx는 `openpyxl`, Parquet은 `pyarrow`가 함께 필요하다(pandas 설치 문서의 선택 의존성). import로 먼저 확인하고 없을 때만 설치해 `requirements.txt`에 적는다(AGENTS.md §6, 커밋은 `chore(deps)` 별도).
   - 표가 아닌 데이터(텍스트·이미지·로그 원문·파형 등): 파일 수·크기·형식과 샘플 3개를 직접 열어 본 내용을 적는다. 표 항목을 억지로 채우지 않는다.
3. 의미 확인: [questions.md](references/questions.md)에서 원문·데이터로 답할 수 없는 것은 question(Q-n), 시간 때문에 고른 기본값은 assumption(A-n)으로 ledger에 남긴다. 담당자에게는 짧은 질문과 선택지를 보낸다($intent 4단계).
4. `## 결론` 3줄: 분석 단위(행·파일 하나가 무엇인가) / 타깃·지표 후보 / 가장 큰 위험(누수·불균형·결측). `$intent`의 AC 작성 근거로 쓰고, 이미 승인된 AC와 어긋나면 `$intent` "바꿀 때"로 간다.

## ② 숫자를 만드는 기능을 구현할 때
1. 유형: AC 지표로 [problem-types.md](references/problem-types.md)의 유형 하나를 고른다. 둘 이상으로 읽히면 Q-n. **표에 없는 유형이면** Q-n으로 남기고 아래 2~7단계만 적용한다. 표의 행에 억지로 맞추지 않는다.
2. 평가 설계부터: 분할 방식·지표·baseline을 `docs/LOG.md` 테스트 계획 행의 검증 방법에 쓴다($verify "기능을 시작할 때"와 같은 행).
3. 누수 점검: 유형 행의 누수 항목을 하나씩 확인하고, 해당 없으면 이유를 한 줄 쓴다. 표에 없는 유형은 두 질문으로 본다 — 예측·판정 시점에 알 수 없는 정보가 입력에 들어갔는가, 평가 데이터가 학습·조정에 쓰였는가.
4. baseline 먼저: 가장 단순한 방법의 점수를 먼저 내고, 결과는 "baseline X → 방법 Y"로 보고한다.
5. 재현: 진입 명령 하나로 지표가 파일(예: `outputs/metrics.json`)로 나오게 하고 seed를 고정한다. 보고하는 수치는 그 파일에서만 인용한다.
6. 해석: 데이터의 주요 그룹별 지표 차이와 틀린 사례 몇 개를 확인해 `$verify` 6단계 보고의 "알려진 실패 모드"에 넣는다.
7. 완료: `$verify`로 지표를 다른 경로로 다시 계산한다(예: 예측 CSV로 혼동행렬을 직접 세어 recall 대조).

## 금지
- 평가 데이터를 보고 특징·임계값·하이퍼파라미터 고르기
- baseline 없이 점수만 보고하기
- 결측을 이유 없이 0으로 채우기, 원본 데이터 덮어쓰기
- 실행하지 않은 지표 인용
