# Doc Writer

제출 문서는 "선택한 판단과 근거, 검증 결과, 남은 한계"를 담아야 한다(응시 가이드). 문서가 곧 Intent·Cognition의 증거다.

## 0. 어떤 문서인가 먼저 확정
- 과제 README가 파일명·양식을 지정했으면 **그것만 따른다**. 하네스 docs/*는 원천 자료로 쓰고, 지정 문서로 내용을 옮긴다.
- 지정이 없으면 아래 기본 세트. 무엇을 만들지 사용자에게 한 줄로 확인한다.

## 1. 문서 유형별 골격 (references/templates.md에 상세 템플릿)
| 문서 | 핵심 질문 | 원천 |
|---|---|---|
| 계획서 | 무엇을 왜 이 순서로? | INTENT, PLAN, DECISIONS |
| 협업 기록 | 담당자·AI와 무엇을 합의/위임/검증했나? | INTENT 변경 이력, `.harness/log/prompts.jsonl`, git log |
| 결과 보고서 | 무엇을 얻었고 얼마나 믿을 수 있나? | VERIFICATION, 실행 결과 |
| README(실행 방법) | 남이 그대로 돌릴 수 있나? | 실제로 실행해 본 명령 |

## 2. 작성 규칙
- **근거 링크**: 사실 문장마다 출처를 단다 — `(R-2)`, `(D-3)`, `src/metrics.py:compute_yield`, `verify.log 14:32`, 커밋 해시.
- **수치**는 VERIFICATION.md의 재현 명령이 있는 것만 쓴다. 없으면 먼저 `$verify-gate`.
- **한계 섹션 필수**: 미검증, 가정(A-n), 데이터 한계, 시간 때문에 뺀 범위.
- **AI 활용 기록**: 무엇을 AI에 맡겼고, 어떻게 검증했고, 어디서 AI 결과를 고쳤는지 구체 사례 2~3개.
- 짧게. 표와 목록 우선. 과장 표현("완벽", "모든", "최적") 금지.
- 문서에 쓴 실행 명령은 실제로 한 번 실행해 본다.

## 3. 수정 모드 (기존 문서를 고칠 때)
1. 먼저 문서 전체를 읽고, 바꿀 부분과 이유를 목록으로 보여 준다.
2. 최소 변경으로 고친다 — 사용자가 직접 쓴 문장은 의미를 바꾸지 않는다.
3. 에디터에서 같은 파일을 열고 있으면 저장 충돌이 날 수 있다: 수정 후 사용자에게 "외부 변경 불러오기"로 확인하라고 알린다.
4. 수정 후 `$doc-review` 체크리스트의 해당 항목만 재확인.

## 4. 마무리
- 커밋: `docs(<문서>): <무엇을> — 근거 연결/한계 추가`
