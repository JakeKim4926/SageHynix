# Verify

"완료"는 주장이 아니라 증거다. 무엇을 테스트할지는 [test-strategy.md](references/test-strategy.md), FE 변경은 [frontend.md](references/frontend.md)를 읽고 아래 절차에 합친다. 별도 완료 판정·기록 루프를 만들지 않는다.

## 기능을 시작할 때
구현 전에 test-strategy 1절대로 실패 가능성×영향도를 보고 docs/LOG.md "테스트 계획" 표에 검증 방법 한 행을 쓴다. 개발 파일과 테스트 파일을 1:1로 맞추지 않는다.

## 절차
1. **주장 목록**: 이번 작업이 충족한다고 주장하는 요구사항 R-n과 수용 기준을 `docs/INTENT.md`에서, 검증 방법을 LOG 테스트 계획에서 가져온다. 계획 행이 없으면 먼저 쓴다.
2. **자동 검증**: `python3 -m pytest -q`, ruff가 있으면 `ruff check --select E9,F .`, FE는 frontend.md 명령. FAIL이면 고치고 다시. 계획에 적은 흐름·단위 테스트가 없으면 test-strategy 2절대로 추가한다. 테스트 0개나 계획에 없는 생략을 통과로 보지 않는다.
3. **요구사항별 검증** — 기준마다 실제 명령을 실행한다.
   - 수치: 다른 경로로 다시 계산해 일치 확인(예: pandas 집계 vs 순수 파이썬 합계)
   - 웹: `0.0.0.0:<port>`로 떠 있는지, `curl -s http://127.0.0.1:<port>/<path>` 응답 확인. 화면은 사용 가능한 브라우저 도구로 확인하고, 없으면 사용자에게 Browser 탭의 PORT·경로·동작·기대값을 제시해 확인받는다. 확인 전에는 미검증
   - 성능 요구가 있으면 실제 데이터 전체로 1회 시간 측정
   - 버그 수정: 고치기 **전에** 그 버그를 재현하는 테스트가 FAIL하는 것을 확인하고, 고친 뒤 PASS를 확인한다. 재현 불가·미실행·skip·다른 이유의 FAIL은 수정 완료가 아니다
4. **기록**: `docs/LOG.md` 검증 표에 기능마다 행 추가 — 시각 | 결과 한 줄(test-strategy 4절 형식) | 구현 위치(파일:함수). 실패·미실행·생략도 그대로 적는다.
5. **커밋** (통과한 것만):
   ```bash
   git add -- <이번-변경-파일>
   git diff --cached --stat
   git commit -m "feat(<scope>): <무엇> — <R-n 충족>, verify PASS"
   ```
   이번 작업 외 변경과 디버그용 임시 파일은 넣지 않는다. 커밋 단위가 크면 나눈다.
6. **사람용 보고**: 4단계의 결과 한 줄을 기능마다 그대로 보인다. 수치 결과면 대표 수치 하나와 계산 경로(파일:함수), 알려진 실패 모드가 있으면 그것을 한 줄씩 더한다. 같은 줄을 커밋 본문에도 쓴다.

## 독립 검증 (중요 수치)
`verifier` 서브에이전트에 `prompts/SCRIPT.md`의 6칸 형식으로 맡긴다. [Context]에 주장 목록과 실행 방법, [Done]에 "모든 주장에 통과/실패/검증불가 판정"을 적는다. 결과는 그대로 LOG.md에 옮긴다.

## 금지
- 실행하지 않고 "통과"라고 쓰기
- 실패 테스트를 지우거나 skip해서 통과시키기, 기대값을 결과에 맞춰 고치기(고쳐야 한다면 이유를 INTENT 결정 D-n에)
