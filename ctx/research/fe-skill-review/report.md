# research/fe-skill-review — 조사 보고

## 결론
[추론] FE 신규 스킬은 fe-setup·fe-build 2개, 검증은 기존 verify-gate의 FE 참조 절차로 통합한다. 사전 코드 반입 허용을 전제하지 않는다.
3시간은 구현 범위·설치 비용을 줄이는 설계 배경이며, 시간표·타이머를 재도입하지 않는다.
검토 제안이며 FE 스킬·스타터·검증 코드는 아직 구현하지 않았다.

## 선택지
| 선택지 | 비용 | 위험 | 판단 |
|---|---|---|---|
| 기존안: bootstrap/build/check 3개 + 사전 스타터 | 독립 검증 절차와 코드 자산 관리 | 기존 verify-gate 중복, 코드 반입 미확인 | 수정 |
| setup/build 2개 + verify-gate FE 절차 | 기존 기록·판정 재사용 | FE 환경 감지와 실제 브라우저 검증을 보완해야 함 | 권고 |
| 단일 FE 스킬 | 진입점은 단순 | 환경 준비와 반복 구현의 발동 범위가 넓음 | 대안 |

## 근거
- [사실] 현재 대화: TS(strict)·React·Vite·Tailwind 제안, 웹 IDE 3000 포트 예상, 고정 시간표와 모든 타이머 제거 요청.
- [사실] 채팅 `Codex Sol 6.0 스킬 구조 점검` (01a18a9c-6f19-7b33-869b-84abfb543bf0): clone 후 루트에서 사용, 설치 판별→필요 항목 설치→재검증 요구. 이전 검토에서 git add -A와 스킬 연쇄 호출 범위 지적.
- [사실] 채팅 `하네스 설정 상세 검토` (01a18a31-fc6a-7d81-8237-6c142eeb1dc6): 사용자가 사전 .py 코드 반입 문제 제기. 원문 규정 확정은 해당 대화에서도 미완료.
- [사실] 채팅 `포트 3000 서버 종류` (6adfe8d4-1838-83ee-95b7-f4a5f0932340): 포트만으로 기술 스택을 확정할 수 없다는 논의.
- [사실] `.harness/bin/verify.sh`: 루트 package.json의 npm test --if-present만 실행하며 frontend/의 타입·린트·빌드 검사는 없다. verify.local.sh 확장 지점은 존재.
- [사실] `.agents/skills/verify-gate/SKILL.md`: 자동 검사·수용 기준 검증·기록·커밋·인지 점검을 이미 담당한다.
- [사실] Vite 개발 서버는 host/port/strictPort/proxy 설정을 지원하고 기본 포트는 5173이다. https://vite.dev/config/server-options
- [사실] Vite의 TS 변환 자체는 타입 검사를 수행하지 않는다. https://vite.dev/guide/features
- [추론] FE용 자연어 절차·설정 계약을 먼저 설계하고, 실제 앱 코드와 lockfile은 허용된 환경에서 생성한다. 스크립트·템플릿 제공은 반입 허용 확인에 종속된다.
- [추론] fe-setup은 기존 프로젝트 및 런타임·브라우저 가용성 확인, fe-build는 실제 데이터→화면·상태 처리, verify-gate는 필수 검사 누락과 미실행을 분리해 기록한다.

## 미확인
- 사전 작성 스크립트·UI 템플릿·자연어 스킬 각각의 반입 허용 범위. 공개 저장소 다운로드 허용만으로 확정할 수 없다.
- 실제 웹 IDE의 Node/npm 버전, 패키지 설치망, 브라우저 실행 권한, 프록시 호스트와 HMR 연결.
- 정확한 Luna 모델 ID 및 이 구성의 모델별 정답률·총 토큰·수정 횟수.

## 담당자 질문
- 사전 작성 자연어 Skill과 실행 코드·UI 템플릿의 반입 허용 범위를 구분해 확인한다. 검토 자체에는 답변이 선행할 필요가 없으나 사전 코드 자산 배포에는 필요하다.
