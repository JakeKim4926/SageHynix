# Doc

제출 문서는 "판단과 근거, 검증 결과, 남은 한계"를 담는다(응시 가이드).

## 0. 무엇을 쓰나
- 과제 README가 파일명·양식을 지정했으면 **그것만** 따른다(`docs/research/task.md`의 필수 산출물 표).
- 지정이 없으면 `references/templates.md`의 기본 세트. 무엇을 만들지 사용자에게 한 줄로 확인한다.
- 원천: `docs/research/*.md`(판단 근거), `docs/VERIFICATION.md`(검증), `git log`, `.harness/log/prompts.jsonl`(AI 협업 기록).

## 1. 작성
- 사실 문장마다 출처: `(R-2)`, `docs/research/data-sensor.md`, `src/metrics.py:compute_yield`, 커밋 해시.
- 수치는 VERIFICATION.md에 재현 명령이 있는 것만. 없으면 먼저 `$verify`.
- **한계 섹션 필수**: 미검증, 가정, 데이터 한계, 시간 때문에 뺀 범위.
- **AI 활용**: 무엇을 맡겼고, 어떻게 검증했고, 어디서 AI 결과를 고쳤는지 구체 사례 2~3개.
- 짧게, 표 우선. "완벽/모든/최적/보장" 금지. 문서에 쓴 실행 명령은 한 번 실제로 실행한다.

## 2. 수정
- 바꿀 부분과 이유를 먼저 보여 주고 최소 변경. 사용자가 쓴 문장의 의미는 바꾸지 않는다.
- 에디터에 같은 파일이 열려 있으면 저장 충돌이 난다 — 수정 후 "외부 변경 불러오기"를 안내한다.

## 3. 감사 (제출 20~30분 전, 항목마다 실제 확인 후 표로)
1. 필수 산출물: task.md 표 vs `git ls-files` — 경로·철자, 빈 파일 없음
2. `git status --porcelain` 비었나. 에디터 "저장됨"은 사용자에게 확인 요청
3. 주장-근거: 문서의 수치·"완료"·"검증" 문장 → VERIFICATION/코드와 대조. 불일치는 `문서:줄 → 실제 → 수정 문구`
4. R-n마다 코드 위치와 VERIFICATION 행이 있나. 끊긴 것은 문서에 "구현/검증 안 됨"으로
5. README 실행 명령 재현(서버면 띄우고 curl 후 종료)
6. 민감 정보: `rg -n -i "api[_-]?key|token|secret|password"`

결과는 수정 목록으로 보여 주고, 승인된 것만 고친다.

## 4. 서술형 대비 (마지막, 5분)
후속 서술형은 AI 없이 직접 답한다. 제출물·git log 기준으로 예상 질문 5개(의도·판단·검증·실패·AI 활용 각 1개)와 질문마다 답변 골격 3줄(핵심 사실과 근거 위치 / 약점과 영향 / 다음 개선)을 주고, 외워야 할 숫자·파일명 앵커 목록을 덧붙인다. 완성 답안은 쓰지 않는다.
