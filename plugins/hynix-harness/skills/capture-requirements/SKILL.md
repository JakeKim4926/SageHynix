# capture-requirements

끝나면 `docs/INTENT.md`가 무엇을, 누구를 위해, 어떤 기준으로 만들지를 ID와 출처로 고정하고, 담당자에게 보낼 질문이 준비돼 있다.

## 입력
- **처음**: 과제 README와 제공 파일 목록. 데이터 파일은 크기만 보고 내용은 `$inspect-dataset`에 넘긴다.
- **갱신**: 사용자가 붙여 넣은 담당자 대화. 없으면 붙여 달라고 요청한다.

## 진행
**처음 (README 기준)**
1. `.harness/bin/clock.sh status`를 확인한다. 타이머가 시작되지 않았으면 사용자에게 `clock.sh start`를 권한다. 시작 시각은 사람이 정하므로 직접 실행하지 않는다.
2. README 전체를 읽고 줄 번호와 함께 뽑는다: 필수 산출물(파일명·경로·형식), 기능·비기능 요구사항(실행 방법, 포트 등), 제약, 평가 언급.
3. 요구사항마다 R-n, 측정 가능한 수용 기준, 출처를 단다. 수용 기준을 숫자나 관찰 가능한 행동으로 쓸 수 없으면 Q-n으로 만든다.

**갱신 (담당자 대화 기준)**
1. 대화에서 원문 1줄 인용과 함께 뽑는다: 새 요구사항이나 변경, 성공 기준·우선순위·범위, 데이터 의미(컬럼·코드값·단위·기간), "모른다/안 정했다"(A-n 후보).
2. Q-n 상태를 `답변됨 → R-x/A-y`로 바꾼다. 바뀐 R-n은 지우지 않고 §6 변경 이력에 남긴다.
3. 이미 계획·구현된 것 중 바뀌어야 할 것(PLAN 슬라이스, 파일)을 나열한다.
4. 답변 원문을 `python3 .harness/bin/ctx.py new note stakeholder-{주제} --q "{물은 것}"`로 남긴다.

**질문 (공통)**: 보내기 전에 `ctx.py find`로 이미 물은 질문인지 확인한다. 질문은 한 문장으로 답할 수 있게(예/아니오, 선택지) 쓰고, 답에 따라 무엇이 바뀌는지 붙인다. 영향이 큰 순서로 처음에는 3~5개, 갱신 때는 최대 3개.

## 제약
- README나 담당자가 말하지 않은 요구사항을 넣지 않는다. 추론은 출처를 `추론`으로, 해석은 `해석:`으로 구분한다.
- README와 담당자 답이 충돌하면 둘 다 적고 사용자에게 어느 쪽을 따를지 묻는다.
- 이 단계에서는 구현하거나 패키지를 설치하지 않는다.

## 완료 기준
- 모든 R-n에 수용 기준과 출처가 있다. 수용 기준을 못 쓴 것은 Q-n이나 A-n으로 옮겨져 있다.
- 필수 산출물 표의 파일명이 README 철자와 같다.

## 출력
- 사용자 보고: 요구사항 요약(5줄 이내), 필수 산출물 표 또는 반영 내역 표, 영향받는 작업, 메신저에 그대로 붙여 넣을 질문 메시지, 답을 기다리는 동안 할 수 있는 일.
- 커밋: `docs(intent): 요구사항 원장 초안 — R-1..R-n` / `docs(intent): 담당자 답변 반영 — Q-2→R-4`
