# write-submission-docs

끝나면 제출 문서의 사실 문장마다 근거가 달려 있고, 한계가 드러나 있으며, 감사 체크리스트를 통과했다. 응시 가이드가 요구하는 것은 "선택한 판단과 근거, 검증 결과, 남은 한계"다.

## 입력
- 과제 README가 지정한 파일명과 양식. 지정이 있으면 그것만 따르고 하네스 `docs/*`는 원천 자료로만 쓴다. 지정이 없으면 아래 기본 세트 중 무엇을 만들지 사용자에게 한 줄로 확인한다.

| 문서 | 답하는 질문 | 원천 |
|---|---|---|
| 계획서 | 무엇을 왜 이 순서로? | INTENT, PLAN, DECISIONS |
| 협업 기록 | 담당자·AI와 무엇을 합의, 위임, 검증했나? | INTENT 변경 이력, `.harness/log/prompts.jsonl`, git log |
| 결과 보고서 | 무엇을 얻었고 얼마나 믿을 수 있나? | VERIFICATION, 실행 결과 |
| README(실행 방법) | 남이 그대로 돌릴 수 있나? | 실제로 실행해 본 명령 |

## 진행
**작성**: [references/templates.md](references/templates.md)에서 해당 문서 템플릿만 읽고 채운다.
- 사실 문장마다 출처를 단다: `(R-2)`, `(D-3)`, `src/metrics.py:compute_yield`, `verify.log 14:32`, 커밋 해시.
- 수치는 VERIFICATION.md에 재현 명령이 있는 것만 쓴다. 없으면 먼저 `$verify-before-done`.
- AI 활용 기록에는 무엇을 맡겼고, 어떻게 검증했고, 어디서 AI 결과를 고쳤는지 구체 사례 2~3개를 쓴다.

**수정**: 문서 전체를 읽고 바꿀 부분과 이유를 목록으로 먼저 보여 준다. 사용자가 직접 쓴 문장은 의미를 바꾸지 않고 최소한으로 고친다. 고친 뒤에는 에디터 저장 충돌을 막기 위해 사용자에게 "외부 변경 불러오기"로 확인하라고 알린다.

**감사**: 항목마다 실제로 확인하고 결과를 표로 낸다.
1. **필수 산출물**: INTENT 산출물 표 vs `git ls-files`. 경로·철자 일치, 빈 파일 없음.
2. **저장 상태**: `git status --porcelain`이 비어 있다. 에디터 탭의 "저장됨"은 사용자에게 확인을 요청한다.
3. **주장-근거 대조**: 수치, "완료", "검증" 문장을 모두 뽑아 VERIFICATION, verify.log, 코드와 대조한다. 불일치는 `문서:줄 → 실제 → 수정 문구`로 적는다.
4. **추적성**: R-n마다 PLAN → 코드 위치 → VERIFICATION 행이 이어지는지 본다. 끊긴 것은 "구현 안 됨/검증 안 됨"으로 문서에 반영한다.
5. **실행 방법 재현**: README의 실행 명령을 실제로 실행한다. 서버면 띄워서 curl로 응답을 확인하고 종료한다.
6. **한계**: 미검증 항목, A-n 가정, 제외 범위가 모두 들어 있다.
7. **표현**: "완벽/모든/최적/보장" 같은 과장과 근거 없는 일반론이 없다.
8. **민감 정보**: `rg -n -i "api[_-]?key|token|secret|password"` 결과에 키, 토큰, 개인 정보가 없다.

문서가 많거나 시간이 부족하면 1·3·4번을 `doc_auditor` 서브에이전트에 맡기고 메인은 2·5·8번을 직접 실행한다. 감사 결과는 수정 목록으로 보여 주고, 승인된 것만 수정 방식으로 반영한다.

## 제약
- 한계 섹션을 빼지 않는다.
- 문서에 쓴 실행 명령은 실제로 한 번 실행해 본 것만 쓴다.

## 완료 기준
- 감사 8항목이 모두 통과했거나, 통과하지 못한 항목이 사용자에게 보고됐다.

## 출력
- 작성·수정: 바꾼 문서와 바꾼 이유 목록.
- 감사: 항목별 결과 표와 수정 목록.
- 커밋: `docs({문서}): {무엇을} — 근거 연결/한계 추가`
