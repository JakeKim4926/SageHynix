# verify-before-done

끝나면 이번 슬라이스의 수용 기준마다 실행한 명령과 관찰 결과가 `docs/VERIFICATION.md`에 있고, 통과한 변경만 커밋돼 있다.

## 입력
- 이번 슬라이스가 충족한다고 주장하는 R-n과 수용 기준(`docs/PLAN.md`).

## 진행
1. `.harness/bin/verify.sh`를 실행한다(문법, 오류급 lint, pytest). FAIL이면 고치고 다시 실행한다. `tests/ 없음`으로 SKIP되면 핵심 계산에 최소 테스트를 추가한다: 손으로 계산할 수 있는 작은 입력의 기대값, 빈 데이터·결측·중복 키 경계.
2. 수용 기준마다 실제 명령을 실행한다.
   - **수치**: 독립 경로로 다시 계산해(예: pandas 집계 vs 순수 파이썬 합계) 일치를 확인한다.
   - **웹**: 서버가 `0.0.0.0:{port}`에 떠 있는지 보고 `curl -s http://127.0.0.1:{port}/{path}`로 응답을 확인한다. 화면 동작은 사용자에게 Browser 탭(포트·경로)에서 확인을 요청하고 결과를 받는다.
   - **성능·규모** 요구가 있으면 실제 데이터 전체로 한 번 실행해 시간을 잰다.
3. `docs/VERIFICATION.md` 표에 행을 추가한다: 요구사항 | 구현 위치(파일:함수) | 명령 | 관찰 결과 | 시각. 실패와 미실행도 그대로 적는다.
4. 통과한 것만 의미 단위로 커밋한다. 디버그용 임시 파일은 넣지 않는다.
5. `python3 .harness/bin/ctx.py new slice {s-n} --q "{슬라이스 목표}" --serves R-n --inputs {핵심 파일}` → `slice.md`(한 일, 검증) → `ctx.py done slice/{s-n}`.

중요한 수치나 제출 직전이라 독립 검증이 필요하면 `verifier` 서브에이전트에 맡기고 결과를 그대로 기록한다.

## 제약
- 실패 테스트를 지우거나 skip해서 통과시키지 않는다. 기대값을 결과에 맞춰 고치지 않는다. 고쳐야 한다면 이유를 DECISIONS에 적는다.
- 같은 실패를 세 번 고쳐도 통과하지 못하면 멈추고 원인 가설과 함께 사용자에게 보고한다.

## 완료 기준
- 모든 수용 기준에 VERIFICATION 행이 있고, 각 행은 PASS이거나 `미검증`·FAIL로 명시돼 있다.

## 출력
- 사용자 보고: 수용 기준별 PASS/FAIL/미검증 표.
- 커밋: `feat({scope}): {무엇} — {R-n 충족}, verify PASS`
- 다음 단계는 `$rehearse-explanation`.
